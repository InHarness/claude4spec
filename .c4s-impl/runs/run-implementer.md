# How to run as the implementer (build mode)

1. Read your instructions in full: `.c4s-impl/prompts/implementer.md`. They are your whole prompt; follow them exactly — including the sections at the end ("This build", "Start mode: resume", "Tests", "Criteria with an empty `verifies`") that override the role text.
2. Your scope block is the file named in your task. Its packet path is in the scope. Slugs of the form `section:<anchor>` name a changed specification section: make what that section says (at the window) hold in code, and for a removed section/sentence, make sure the counterpart is gone. `ac-…` slugs are criteria (one test tagged `[ac:<slug>]`); other slugs are built entities (counterpart + `[entity:<slug>]` shape test + a `trace.md` line). A non-empty `only` lists the items the unit verifier or the reviewer found not to hold: re-read each at the window (a finding's text is in `.c4s-impl/review/<unit>.json`) and make it hold.
3. This branch already implements most of the window. Find what already holds first; change only what is missing or wrong; respect the packet's **Not yet** parts (if code for a deferred part already exists on the branch, leave it). Make each behaviour hold END TO END along every path a user reaches it (server, route, CLI, client), not only in one service. The portion may have been started by a run that stopped early: read the repo first and finish what is missing. Never run tests (only `npm run typecheck`). Do not commit. A clause that would change user-observable behaviour where the spec is ambiguous or contradicts itself, or where the code deliberately keeps pre-window behaviour → a deviation file in `.c4s-impl/deviations/` (schema `.c4s-impl/schemas/deviation.json`, next free `dev-NNNN`, `sent: false`) + an `ASSUMPTION:<id>` marker at the site.
4. No verifier runs after your portion — the unit verifier reads the whole unit later. Before you report: read every test whose name carries a slug of your scope against the code it exercises and fix what could not pass; `npm run typecheck` clean.
5. Near your limit, stop and report with `stoppedEarly: true` rather than start a change you cannot finish — the next run continues the same portion.
6. The c4s server is occasionally flaky ("fetch failed" / SERVER_NOT_RUNNING): retry a failed command a few times with a short pause.
7. Write your final JSON (per `.c4s-impl/schemas/iteration-status.json`, role implementer) to the output path named in your task, and return only that JSON as your final message — no prose around it.
