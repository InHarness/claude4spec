# How to run as the verifier (portion scope)

1. Read your instructions in full: `.c4s-impl/prompts/verifier.md`. They are your whole prompt; follow them exactly — including the sections at the end ("This build", "Tests", "Criteria with an empty `verifies`") that override the role text. Verification is static: never run tests; `npm run typecheck` is the only command you may run besides `c4s`, `git` and read-only shell tools. The repo is read-only for you.
2. Your scope block is the file named in your task. Derive the checklist yourself from the specification with `c4s release-diff` reads at the window; do not trust any packet or claim. One row per portion slug (and one per `only` item if not already a slug): `section:<anchor>` = a changed specification section (level 1 for structure/deletion, level 2 for behaviour — does the code make what the section says at `<to>` hold, and the removed parts gone?); `ac-…` = a criterion; other slugs = built entities (shape vs the entity at `<to>` + `trace.md` line + `[entity:<slug>]` shape test). Judge behaviour END TO END along every path a user reaches it (server, route, CLI, client). Evidence = path:line. Respect the recipe's `deferred` parts (its `completes` parts are in scope). Uncommitted working-tree changes are part of what you verify. Read touched tests: do they assert something meaningful and would they pass against current code?
3. If a row fails only because the specification contradicts itself, or because the code deliberately keeps pre-window behaviour, and a deviation in `.c4s-impl/deviations/` records it, cite its id (`dev-NNNN`) in the evidence.
4. The c4s server is occasionally flaky: retry a failed command a few times.
5. Write your final JSON (per `.c4s-impl/schemas/verdict.json`) to the output path named in your task, and return only that JSON as your final message — no prose around it.
