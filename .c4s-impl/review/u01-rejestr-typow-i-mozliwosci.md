# u01 — non-blocking findings (round 1)

- **rev-0001** `src/server/routes/config.ts:106` — configResponse strips inactive keys from the RESPONSE body using the field's FILE path (fieldPath(decl)), but the response shape does not mirror the file everywhere — e.g. file key `onboardingCompleted` is returned as `onboarding.completed`, and `agent.*` is enriched with derived fields. Once a row with such a key gains `requires`, the GET/PATCH answer would still leak it (deletePath is a silent no-op on a missing path). Latent today (no row carries `requires` yet), but the mechanism is meant to be relied upon in u03/u04/u07; either map response paths explicitly or filter before building the response, and cover a non-mirrored key in a test.
- **rev-0002** `src/server/project-types/capabilities.ts:188` — `satisfies()` is exported but unused; the same `(requires ?? []).every(c => caps.has(c))` check is re-implemented inline in FieldRegistry.active/inactiveKeys (src/server/settings/field-registry.ts) and in assembleSettings' `meets` (client). Either use the helper on the server side or drop it — dead code plus three copies of the active-row rule invites drift when the rule changes.
- **rev-0003** `src/client/components/settings/registry.ts:45` — assembleSettings now takes a per-project capability set, but its only caller (SettingsPage.tsx:55) memoizes the result in a cache keyed by scope alone. When u02 starts passing capabilities, switching between projects of different types would serve a stale card set; the cache key must include the capability set (or the cache must go) when the stub closes. Noting it here so the seam is closed correctly.
