# Review — m10-plan-full-read-and-conflict (non-blocking)

- **rev-0002** `src/client/lib/own-writes.ts:15` — The new comment (repeated in useFileWatcher.ts and in the ownWrites test header) suggests a `threadId: null` plan:updated can only be this tab's echo, and that only events naming a thread come from other writers. That is not true. The REST frontmatter PATCH (another tab renaming or flipping applied) and an explicitly addressed external-mount update_plan (plan.ts:784) also broadcast `threadId: null`. The code is safe anyway: every path holds the same per-path lock, so a foreign write that lands before the PUT makes it fail with 409, and failed() hands the event back. A foreign write that lands after the PUT is broadcast after this tab's echo. But the comment should say that, not imply that null means own.
- **rev-0003** `src/client/components/PlanPage.tsx:170` — On a PLAN_CONFLICT the code sets the banner but does not clear `error`. handleReload does not clear it on success either. An error left over from an earlier failed Save, rename or run then stays on screen next to the conflict banner, and remains after Reload has replaced the buffer. Call setError(null) together with setConflict(true), and again on a successful reload.
