# u01 review — non-blocking findings

- r1 rev-0002 `src/server/fs/multi-file-operation.ts:109` — Undoing a file the operation created checks the hash outside the path lock and then calls store.remove() with no conflict check, so this is a check-then-act race. A writer already queued on that path's lock (or one that lands between the check and remove's withPathLock) writes its content first, and the rollback then deletes it. That breaks the documented promise that a file somebody else changed is 'listed in unrestored, never overwritten'. RecordStore.remove should honour opts.expectedHash under its lock, as write/move/restore do. Also, when the file is already gone (now === null), remove returns false, yet the path is still reported as restored.
- r1 rev-0003 `src/server/fs/multi-file-operation.ts:82` — The journal's `before` snapshot is read with store.readRaw outside the path lock that store.write takes. A concurrent writer queued on the same path can change the file between the snapshot and the commit. If that happens, the rollback 'restores' a state the operation never overwrote, and drops the other writer's content without a conflict. Capturing `before` inside the locked commit, for example by returning the pre-commit bytes from the primitive, would close the gap.
