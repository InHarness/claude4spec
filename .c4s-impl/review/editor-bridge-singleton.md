- [rev-0301] src/client/runtime/editor-bridge.ts:88 — The design depends on React DOM internals: the `__reactFiber$<random>` key, `fiber.return` and a provider fiber's `memoizedProps.value`. These are stable from React 17 through 19, and the repo pins react-dom 18.3.1. A public-API design is not available. A provider that adds no DOM node cannot listen to events or be checked with `element.contains`, and `contains` would also miss portals. So the choice is defensible. The file header and decisions.md say it 'degrades to the last-mounted fallback', which makes that failure sound harmless. It is not. Passive effects run child-first, so the last registered provider is the OUTER one of a nested pair. If the walk ever stops finding fibers, chips inside the inner provider silently reach the outer bridge, or whichever sibling pipeline (chat or page) mounted last. The nested, side-by-side and portal render tests use the real react-dom and would go red on such an upgrade, which is the real safeguard. A one-time dev `console.warn` would make a broken walk visible at runtime too: fire it when providers are mounted and no `__reactFiber$` key is found on any ancestor of an in-document target. Reword the 'degrades' claim to match.
