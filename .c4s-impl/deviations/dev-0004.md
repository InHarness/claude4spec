## What I found

Rule 17 of `check_consistency` (M19 `k88vwlpj`) reports an `element_list` or `tagged_list` "whose type is active but does not declare the `renderRow` slot". The same requirement appears in M19 `m19hidden` and in the `renderRow?` row of M13 `z7l89jhf`. Criterion `ac-check-consistency-zglasza-ostrzezenie` needs it too.

`check_consistency` runs on the server. `renderRow` is a slot of the browser-side `FrontendModule`. A plugin registers that module from its browser entry with `registerFrontendModule` (M13 `mbladez6`). The server never loads it. The channel that reaches the server is `contributes.entities` (`EntityContribution`), and M13 `m13plenv` says outright that it carries **no frontend slot**. The frontend manifest and package discovery (M33 `m33l5man`, `9g96q3pp`) carry only the entry, the CSS and the version. They do not list slots.

So at `2.1.63` the specification gives the server no way to learn whether an active type declares `renderRow`. A `c4s ask` against the specification confirmed this: it found no manifest or contribution declaration, no `package.json` field and no client report. In code, the server has no such information either. The comment on rule 12 in `src/server/discovery/ops/consistency.ts` already says "the server carries no 'hidden' flag … hiddenness is a frontend-slot property".

## Why this is blocking

Every way to close the gap changes a contract that plugins and later units rely on:

- **A declaration in `EntityContribution`**, e.g. an optional `listView: false`. This is a new Host API slot (M13/M33 — changelog entry plus a registry entry). Its default decides correctness:
  - If omitting it means "has a list view", rule 17 misses every type that does not declare it. That includes the prebuilt `diagram` envelope, which this repo may not edit.
  - If omitting it means "no list view", every listable external plugin gets false warnings.
- **A declaration in the envelope's `package.json` `c4s` block**. The same trade-off applies, and the change lands in M33 discovery.
- **The server importing each plugin's browser entry to inspect it** is not a contract the specification describes. It would run React or DOM code in Node.

The specification chooses none of these. Picking one silently would publish a Host API shape.

## What was built (non-blocking part of the unit)

- Both pipelines render the information block "type `<type>` has no list view" with the count of matching entities. There are no rows and no chips. Count `0` is included, and an inactive type still gets a broken chip. This covers `ac-element-list-albo-tagged-list-na-typ`.
- The hidden-entity chip click goes to the read-only `<type>-expand` window. This covers `m19-hidden-entities-render-slots`.

Rule 17 is not built: no catalogue entry and no detector.

## Needed

A decision, in M13 `z7l89jhf` / `m13plenv` (and M33 if it is a manifest field), on how the host learns that an active type declares no `renderRow`, including the default for a contribution that says nothing. The decision must also say how the prebuilt `diagrams` envelope is covered: a new envelope release, or a default.
