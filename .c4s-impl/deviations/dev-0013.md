## What I found

`update-entities` (2.1.57) says the guard's number is "the same number that a read and every entity mutation already return (m29wr001)". No entity read (`get_entities`, `GET /api/{pathPrefix}/:slug`) or mutation response (`{ slug }`, REST `{ data }`) carries the `entity_version` number today; a caller sees it only in the entity's version list (`GET /api/entities/:type/:slug/versions`). Also, the operation's `rest` cell points at `PATCH /api/{pathPrefix}/:slug`, which does not accept `expectedVersion` (that endpoint's record did not change in this window).

## What was built

The guard compares with the entity's highest `entity_version` number (0 when the log never captured it). Read and mutation responses are unchanged, because those contracts are not in this unit's recipe. Over REST an item writes unchecked, which the operation's rule allows.

## Suggestion

Either add the `entity_version` number to entity read and mutation responses (and `expectedVersion` to the PATCH body) as a separate change, or have `update-entities.zachowanie` name the version list as where the number comes from.
