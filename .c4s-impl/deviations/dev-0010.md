## What I found

M10 `m10ws000` describes `m10-plan-updated` as a notification reaction with trigger `prymityw`, ordered `after: [capture]`, emitting `plan:updated { planPath, threadId, version, changedBy }`. Two things in code predate the 2.1.7→2.1.8 window and differ. First, M40's runtime ranks the `notification` phase before `capture` and refuses a dependency on a later phase, so a notification reaction cannot run after capture. Second, `PlanService` writes plan files with `chain: false`, because its `file_version` row carries a `change_summary` that the capture phase cannot receive. It broadcasts `plan:updated` itself, after its own `recordVersion`. The build keeps this, and the bound `m10-plan-updated` definition no longer fires on watcher events. An outside edit is announced by the base `file:changed { rootId: 'plans' }`, as the window says.

## Suggestion

Either describe `plan:updated` as the last step of the plan service's own write chain, after its own capture, with the reaction holding only the acceptance contract. Or move the `notification` phase after `capture` in M40, so that `after: [capture]` can be expressed.
