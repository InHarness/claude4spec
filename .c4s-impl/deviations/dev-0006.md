## What I found

At 2.1.8 `get_page` is `(rootId, path)` and has no line window (984v8437, llrqdo0o), but the specification does not say what happens when a caller still sends the removed `range` (an MCP client with a cached schema, `c4s get-page --range`, `GET /api/pages/:rootId/get?range=`). Ignoring it would answer with the whole page to a caller who believes it narrowed the read. The build REFUSES it on every channel with INVALID_ARGUMENT whose message names the way on (`get_page_outline`, then `get_sections`): the core refuses in src/server/discovery/ops/pages.ts (`getPage`), the MCP tools keep a loose input object so the stale key reaches the core (src/server/mcp/c4s-reader.ts, src/server/mcp/reference-tools.ts), REST forwards `?range=` (src/server/routes/pages.ts), and the CLI refuses `--range` with INVALID_ARGS (src/bin/c4s/commands/get-page.ts).

## Suggestion

State in M39 `984v8437` (and the `get_page` mcp-tool entities) that a leftover `range` is refused with INVALID_ARGUMENT naming `get_page_outline` + `get_sections` — or that it is ignored, if that is the intent.
