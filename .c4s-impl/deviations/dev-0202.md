## What I found

M01 `dsh8ezbz` says the activation fires 'przy aktywacji lub rejestracji projektu ... dopiero przy pierwszym żądaniu', and M31 `m31ctx001` says the context build is 'raz per aktywacja projektu', but neither says whether a REBUILD of a project's context in the same process (after `invalidate` — roots/entities/plugin-pool/trust change — or after an LRU eviction) is a new activation that re-runs the file steps (fresh config if missing, managed .gitignore block, root directories, welcome page when the base space is empty, legacy db move). Re-running them would, e.g., re-create a welcome `index.md` the user deleted from an emptied base space on every config PATCH that rebuilds the context. Assumed: a project is activated once per process (per id + directory) on its first request; a later rebuild is a build only (the build itself still runs its idempotent config migrations and creates root directories added later). A failed activation is not remembered, so the request after the failed-build window activates again; a project whose directory changed in the registry is activated anew.

## Suggestion

State it in the specification. Implemented meanwhile as: ASSUMPTION:dev-0202 — the rebuild after an invalidation or LRU eviction does not re-run the activation's file steps.
