## What I found

At `2.1.63`, section `m13pool0` (M13 L2, changed in this window) says a duplicate type within the base is `PLUGIN_TYPE_CONFLICT`, the same as within the overlay. The silent last-wins (`registerEntityModule` = `Map.set`) is removed.

Two active criteria were not changed in the window, and both still state the retired rule:

- `ac-dwa-pakiety-bazy-workspace-npm-wnoszac`: "two base packages (workspace/npm) contributing the same `type` → silent last-wins (`Map.set` by type), not a hard error".
- `ac-koperta-wbudowana-z-plugins-src-wno`: "a built-in envelope contributing a type already in the base follows the same collision semantics as the rest of the base — silent last-wins `registerEntityModule`; built-in envelopes are discovered FIRST, so an external package can shadow them".

M33 `m33edge0` is cited in `m13pool0` as the source of the last-wins requirement. It may say the same thing. I did not read it, because it is outside this unit's recipe.

## What the build assumes (non-blocking)

The changed section wins, because the unit's goal names exactly this removal. In the code, a duplicate base type is now `PLUGIN_TYPE_CONFLICT`:

- The second package's load record is `failed` with that code, and the first registration keeps the type.
- Envelopes load first, so an external package that contributes an envelope's type is the one that gets refused.

The two criteria's tests were rewritten to assert the new rule under `[section:m13pool0]`. Their `[ac:]` markers were removed, and both slugs are in `tests/ac-skiplist.json` with a pointer to this deviation.

## Suggestion

Rewrite both criteria to the `m13pool0` rule, or deprecate them:

- A second base package with an already-held type → `PLUGIN_TYPE_CONFLICT`. Only a project overlay may shadow a base type.

Also check `m33edge0` for the same stale wording.
