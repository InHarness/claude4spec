## What I found

The mcp-tool entity `brief-tools-update-brief` lists six parameters — `action` (required), `content` (required), `anchor`, `heading`, `expectedHash` (required), `path` (optional, defaulted from the thread) — and its description and M21 `01ytpznn` say there is no textual-substitution mode (`textEdits`) in this version. The code renders a different set on every channel: the catalog row `update_brief` (src/server/operations/core-operations.ts, `contentInput: 'literal+diff'`), the MCP tool (src/server/mcp/brief-tools.ts) and its REST/CLI parity carry the differential `textEdits` shape (added in 0.2.86) plus `changeSummary`, so `action`/`content` are optional (exactly one of the two shapes is required). In the `internal` channel the thread's brief is closed over and the schema has no `path` at all; on the external MCP surface `path` is required. This predates the 2.1.7→2.1.8 window (the window only changed the entity's `logic` from `briefsDir` / `rootId='brief'` to the `briefs` root / `rootId='briefs'`, which the build follows). Removing a working write mode and changing the addressing of a public tool is a contract change, so the build keeps the rendering and its shape test asserts the code's sets.

## Suggestion

Record `textEdits` (+ `changeSummary`) on the entity and drop the "no textual-substitution mode" sentences from the entity and from M21 `01ytpznn`, and state that `path` is absent in the `internal` rendering (closed over) and required on the external one — or schedule the removal of `textEdits` as its own change.
