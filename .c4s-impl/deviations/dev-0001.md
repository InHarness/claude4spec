## What I found

The `file-version` database-table record (unchanged in 2.1.55 except the `serializer_version` description) disagrees with the schema that has shipped since 0.2.2, in ways this window does not touch:

1. Index names — the record lists `idx_file_version_release_id` and `idx_file_version_root_path(rootId, path)`; the code has `idx_file_version_release(release_id)`, `idx_file_version_path(path)` and `idx_file_version_root_release(rootId, release_id)`. The unique index is a table constraint `uq_file_version_path_root_version` (SQLite materialises it as `sqlite_autoindex_file_version_1`).
2. `release_id` carries no FOREIGN KEY to `spec_release` (the record declares FK ON DELETE SET NULL).
3. `op` and `changed_by` have CHECK constraints, although the record says "validation in the application, no CHECK".
4. The table has an extra nullable column `change_summary` (written by `FileVersionService.recordVersion`) that the record does not list.

The implementation of 2.1.54→2.1.55 left the schema as is (no migration) and its `[entity:file-version]` test asserts the record's columns and the (path, rootId, version) uniqueness only.

## Suggestion

Bring the `file-version` record to the shipped schema (indexes, no FK, CHECKs on `op`/`changed_by`, add `change_summary`), or — if the record is the intended design — schedule a later brief that migrates the schema to the record.
