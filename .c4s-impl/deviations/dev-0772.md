## What I found

The container entrypoint registers PROJECT_DIR through POST /api/workspace/projects (M01 uxlvmu4n), whose path is told by the presence of projectType (M31 m31boot01): a type over a directory with config.json is PROJECT_PATH_ALREADY_INITIALIZED, no type over one without is PROJECT_PATH_NOT_INITIALIZED. Taken literally, an empty PROJECT_TYPE over a directory without config (must register `spec`) and a restart with the same PROJECT_TYPE over a provisioned project (must succeed unchanged) would both be refused. Assumed: the entrypoint picks the path by the directory — no config.json → new-project path with PROJECT_TYPE (empty → `spec`); config.json → existing-directory path without a type, after checking PROJECT_TYPE against the file's type itself (different → PROJECT_TYPE_CONFLICT, container ends, nothing sent). The spec should say which registration the entrypoint uses and where its PROJECT_TYPE_CONFLICT is decided.
