## What I found

M33 (`m33l11sc`, harness bullet) and `ac-mountcontext-pluginu-uruchomionego-pr` say the DB handle the harness returns "does not end up in" / "is not contained in" the MountContext of the running plugin, but do not say how deep "contains" goes. MountContext has no `db` slot and no slot holding the handle — yet `MountContext.reader` is the host's RawEntityReader, whose published `HostEntityReader.db` is the documented legacy escape hatch (kept for the reverse `ref` read of `dto.detail`). The same handle is therefore reachable as `ctx.reader.db`.

Implementation (2.1.17 window) reads "contains" as the context's own slots: the harness adds nothing to MountContext, and the test asserts no top-level slot is (or is named) the handle.

## Suggestion

State explicitly which reading holds:
- (a) "contains" = MountContext's own slots; the legacy `reader.db` hatch is out of scope of this guarantee — add one sentence to M33 harness bullet / the AC; or
- (b) the handle must be unreachable from the plugin at all — then the `HostEntityReader.db` hatch must be removed first (M39 / L11 version surface), as its own change.
