## setup

- conventions: the user-jobs line named `pages/SKILL.md` section 12 (`45yst8co`) = the heading "Moduly"; the table is section 13 (`oq23nb0j`, spreadsheet `moduly-feature`) — the known off-by-one of brief section offsets. It is the module index, not a user-jobs table: no unit owns a job (`jobs: []`), as in 2.1.46.
- recipe ranges given as several disjoint ranges ("sections 9, 11", "0, 2–4", context "1–2, 8–10, 13") are split into several page reads of the same key, each with one range; `deferred`/`completes` stay on the read that carries the change range.
- release.json: the `ask` rows answered as in 2.1.46 (approved plan): tests only in env-runner (full `npm test` + `npm run test:e2e` once, at system verification), filtered = static reading + `npm run typecheck`, waiting recipient = the user in this session. startMode `resume` (delta window).
- Build overrides carried over to all four prompts (empty `verifies`, retired criteria, `not yet`, removal without alias, static-verification cautions, dead code and performance blocking); added: rollback of accept-shadow is proven against a real repo + DB, lock/mutex released on every path.
- baseline (startMode resume): tests run only in env-runner, so the local baseline is `npm run build:envelopes && npm run build:server && npm run typecheck` — green at the init commit (main 10372ec1 after 2.1.46, which passed its own env-runner system verification). The full env-runner suite runs once, at system verification.
- next-window gate: `2-1-47-to-2-1-48.md` is already pending (from_release = 2.1.47). Per the user's standing rule (one brief per PR) the gate is acknowledged: this brief is finished, PR'd and merged first; the next window follows in its own loop.
- u1-release-metadata/p1: dto `release` field `accepted_shadow` is served as `acceptedShadow` (`{ id, tipSha } | null`), following the existing snake→camel mapping of this DTO (`created_by` → `createdBy`, `count_breakdown` → `countBreakdown`). Typed optional on the shared `Release` (additive, hand-built `Release` literals stay valid) but always set — `null` or the object — by `ReleaseService.toRelease`, so every `/api/releases` answer carries it.
- u1-release-metadata/p1: the release file carries `acceptedShadow` only when the row has both columns set (`toReleaseFileData`); a plain release file keeps the pre-2.1.47 six keys. A file field that is not `{ id: string, tipSha: string }` reads as `null` (`readAcceptedShadow`), so a malformed file clears the columns instead of failing the rebuild. updateRelease and the M29 DB→disk backfill reuse the same serializer, so they keep the field as the row holds it.
- u1-release-metadata/p1: 058 also lands in `000_baseline.sql` (a fresh DB applies only the baseline and records the chain), appended after `roots` so the baseline-identity positional comparison holds.
- u1-release-metadata/p1 r2: the mcp-tool records at 2.1.47 (`release-tools-release-create`, `-list`, `-update`: `returns` + `sampleReturn`) enumerate the release fields without `acceptedShadow`, so the spec settles it — no deviation. `acceptedShadow` stays on the REST dto `release` (GET /api/releases keeps calling `releaseListOperation` unprojected); the MCP release tools project it out via `mcpRelease` in `src/server/mcp/release-tools/index.ts`. `release_update` carried the same leak (its record lists the same fields) and is projected too, with an exact key-set assertion added to its test.
- u2-git-merge-primitives/p1: lock handle — `GitRepoLock.run/tryRun` pass a frozen opaque `GitLockHandle` to `fn`; `holds(handle)` is true only for the current holder (a released handle opens nothing). Seam for u4: `GitService.tryWithRepoLock(fn)` (try-take, `null` when taken). `commit(opts, handle?)` / `commitOnRelease(release, handle?)`: a live handle → run under the held lock, otherwise wait as before. The merge primitives with a live handle run directly; without one they run only if the lock is free (`busy` otherwise) — that is where the spec's `busy` result comes from. u4's own lock behaviour (holding it for the whole sequence, refusing on an agent turn) is not built.
- u2-git-merge-primitives/p1: `pendingChanges` answers `{ status: 'clean' }` for an empty list (the spec names only `dirty` for a non-empty one); one `git status --porcelain=v1 -z --no-renames --untracked-files=all` gives both sets (in-pathspec entries of any kind + staged entries anywhere), paths repository-relative and sorted.
- u2-git-merge-primitives/p1: `mergeIntoIndex` returns `changedPaths` ABSOLUTE (its only consumer is the acceptance's watcher suppression, which takes absolute paths); `conflicts.paths` repository-relative like the sync results. A tip already in HEAD (no MERGE_HEAD after `merge --no-commit --no-ff`) → `error`. `abortMerge` with no merge open → `aborted` (nothing to undo).
- u2-git-merge-primitives/p1: `merge-abort-failed` uses `operation: 'commit-on-release'` (the enum has no other fit; the acceptance is a release creation) and is attached by `abortMerge` itself (`error.recovery`), so u4 forwards it. Both new kinds get a kind-aware intentPrompt and a hint in `GitSyncRecover` (KIND_HINT is an exhaustive Record — typecheck).
- u2-git-merge-primitives/p1: marker search = `git log [refs] --topo-order --diff-merges=first-parent --diff-filter=A --no-patch --format=%H -- <path>`, last line wins. `--no-patch` is needed: `--diff-merges=first-parent` turns patch output on (checked against git 2.50); `--topo-order` makes "oldest" ancestor-before-descendant regardless of commit dates (a sync merge commit IS listed against its first parent, so the order matters).
- u2-git-merge-primitives/p1 r2 (rev-0001): `mergeIntoIndex` on a conflict whose own `merge --abort` fails returns `error` with `recovery` kind `merge-abort-failed` (operation `commit-on-release`); `recovery` is optional on the error variant of `GitMergeIntoIndexResult` (other errors leave no merge open). Test injects index.lock via a spied `git` step right before the abort.
- u3-operation-suppress/p1: API = `FileWatchRuntime.suppressOperation(scope, absPaths)` / `ScopedWatchRegistrar.suppressOperation(absPaths)` → handle `{ release() }`. Takes ABSOLUTE paths (u2's `mergeIntoIndex.changedPaths` form) and keys each one `(scope, source, relPath)` under every mount of the scope containing it, at issue time; the abs→mount mapping is shared with `headChangeOriginMarker` via the new `src/server/fs/mount-paths.ts` (`mountRelPaths`, moved out of head-change-origin.ts). Paths under no mount → no-op handle, no timer.
- u3-operation-suppress/p1: the check lives in `peekSuppress` (fs event add/change/unlink and `flush`); `runChain` never consults it (the caller runs the chain). Release keeps it for `SUPPRESS_GUARD_MS` (the primitive's guard window); upper limit `OPERATION_SUPPRESS_LIMIT_MS` = 10 min (the spec names no number; it bounds a forgotten release, not the operation), expiry logs `console.warn`. Timers are unref'd and cleared by `disposeScope`/`close`. Several overlapping operations are independent tokens (a Set), so one release never uncovers another's paths.
- u4-accept-shadow/p1: the core lives in `src/server/services/release-accept-shadow.ts` (`acceptShadow(deps, body)`), reached through `ReleaseService.acceptShadow(body)`; the M40 side is an injected `AcceptShadowRuntime` (`suppressOperation`, `runChain(absPath, event)` as the agent's write with origin `server`, `pageKeys(absPath)`), wired in project-context over `w` and the registry-root mounts (`headChangeMounts`, now carrying `rootId`). A chain "fails" when `runChain` throws or reports stale projections.
- u4-accept-shadow/p1: the release mutex (`release-mutex.ts`) is a promise queue kept in the process and keyed by the project dir (like the repo lock, it survives a context rebuild). Taken by POST /api/releases and MCP `release_create` around createRelease + commitOnRelease, by `updateRelease` only with `assignUnreleased: true`, and by the acceptance for its whole sequence. Bootstrap-time `release-import` (clone, before listen) does not take it.
- u4-accept-shadow/p1: `createRelease(input, actor, variant?)` — the variant (only `acceptShadow` passes it) writes the file via the release store (`toReleaseFileData` with `accepted_shadow_*`), rebuilds the cache row in-band through the release indexer's own upsert (`indexReleaseFile`, extracted from `ReleaseIndexerService`), then one transaction inserts the shadow's entity versions (`changed_by = 'agent'`, summary "Accepted from a shadow") and assigns the unreleased versions. Any throw after the write → `store.remove` + `unindexReleaseFile`, rethrown.
- u4-accept-shadow/p1: name/description (incl. RELEASE_NAME_CONFLICT) are validated before the mutex — a refusal never waits; the variant re-checks the name under the mutex. The guard order under the lock: agent turn (BUSY) → git gate (GIT_UNAVAILABLE / ACCEPT_NO_BRANCH) → commitTarget → SHADOW_NOT_FOUND → ACCEPT_STALE → ACCEPT_DIRTY → OUTSIDE_SPEC → RELEASES_IN_SHADOW → trial-merge CONFLICTS. A git command that FAILS before the merge (status, diff, trial merge) is a plain Error (500 INTERNAL), not ACCEPT_FAILED, which the record reserves for after the merge.
- u4-accept-shadow/p1: the shadow's changed paths (`GitService.shadowChangedPaths`, `merge-base..tip`, `--no-renames`, absolute) are read BEFORE the merge: they feed the content flags (`acceptanceFlags`, now shared with the comparison) and the operation suppression. The real merge's `changedPaths` drive the chains and the rollback.
- u4-accept-shadow/p1: entity versions — "before" read from the index before the chains, "after" from the index after; op create (no index row before) / update / delete (tombstone = the before snapshot); an update whose snapshot equals the latest version is skipped (same no-op rule as `captureEntitySnapshot`).
- u4-accept-shadow/p1: ACCEPT_DIRTY / ACCEPT_OUTSIDE_SPEC / ACCEPT_CONFLICTS carry their paths in `error.details`; ACCEPT_ABORT_FAILED carries `error.recovery` (errors.ts now forwards an object `recovery` of a DomainError). `git:status-changed { headChanged: false }` goes out after a rollback, after a failed abort and after a merge commit that did not land; a landed merge commit emits `headChanged: true` from `commit()` itself. The route broadcasts `release:created`.
- u4-accept-shadow/p1: `mergeIntoIndex(tip, handle, knownChangedPaths?)` — additive third argument: the acceptance already read the shadow's changed paths before the merge (for the suppression), so the primitive answers with them instead of a second `merge-base` + `diff`.
- u4-accept-shadow/p1 r2 (rev-0001): `createAcceptingRelease` closes its remove-on-failure try right after the transaction; building the `ReleaseDetail` happens outside it, and a failure there throws `AcceptedReleaseCommittedError` (release-accept-shadow.ts). The acceptance treats it as past the point of no return: no rollback, the merge commit still lands (`commitOnRelease` with the validated name/description), then the error is reported (500 INTERNAL — the release exists). Test `[section:wh8x023p] a failure AFTER the release transaction committed…` in shadow-accept.test.ts.
- u4-accept-shadow/p1 r2 (rev-0002): the merge primitives take `held?: GitHeldRepo` (`{ root, lock }`) instead of a bare handle; with a live handle of `root`'s lock they skip their gate (`mergePrimitiveRoot`), otherwise they gate as before. The acceptance builds `held` from the gate it read under the lock.
- u4-accept-shadow/p1 r2 (rev-0003): `mergeIntoIndex(tipSha, changedPaths, held?)` — `changedPaths` is required and echoed in `merged`; the `merge-base` + `diff` fallback is deleted. u2's tests pass the paths (the move case reads them with `shadowChangedPaths`, as the acceptance does).
