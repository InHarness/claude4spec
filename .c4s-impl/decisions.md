## m23-patch-full-read / p1-l5-l5
- The patch page already read the detail route without `view`/`range`; since m36 that is the whole-file default projection, so the screen needed no read change. Mirroring the brief unit (performance rule): `useUpdatePatchContent` writes the detail cache from the sent content + the PUT's hash/frontmatter (title re-derived via the now-exported `toPatchArtifactView`) instead of refetching the whole patch; `useCreatePatchThread` invalidates only the threads list (the detail and the list items carry no threads). `useSetPatchApplied` still refetches the detail: the frontmatter write changes the file's bytes, and the editor recomposes saves from the cached `content`.
- `PatchDetail.render.test.ts` now runs the real hooks and `patchesApi` over a faked `fetch` (one file, both former `[entity:patch-page]` cases kept), so the GET URL and the PUT body are what the screen really sends. The view's "Historia wersji" panel stays unbuilt (ASSUMPTION:dev-0004, unchanged in this window).
- rev-0001 (round 2). The echo is real for briefs and possible for patches, but not on the channel the finding names. A brief or patch content save goes through the record store with `chain: false` under the primitive's suppress token (`brief.ts` / `patch.ts` `writeBytes`, `record-store.ts` `write`), so an own save broadcasts NO base `file:changed`. The echoes it does broadcast are `briefs:changed` with `origin: 'server'` (always: `BriefService.updateContent`) and `patches:changed` (only when the frontmatter projection moved, e.g. the `applied` flip). A `file:changed` with `origin: 'server'` for the patches/briefs root therefore always comes from another writer, such as an agent's tool or a chain-running service, and still refetches the detail; that branch is unchanged. The fix is one shared ledger, `src/client/lib/own-writes.ts`, used by briefs and patches alike. A write registers in `onMutate`. The watcher's `briefs:changed` / `patches:changed` branches absorb at most one event of that path per own write: either one arriving while the write is in flight, or, for a brief content save whose echo is guaranteed (`lateEcho`), the first one after the PUT answered. A failed write that absorbed an event invalidates the detail exactly as the watcher would have. A socket reconnect clears the ledger. Plans are untouched. Tests: `src/client/hooks/useFileWatcher.ownWrites.test.ts` covers own echo → no detail GET, another server-origin write → detail refetched, one absorption per save, failure hand-back, applied flip, brief late echo and reconnect.
- rev-0001, the list remark: `useUpdatePatchContent` keeps invalidating `['patches','list']`. A body-only autosave makes the watcher queue nothing, and the list row's "modified …" follows the file's `updatedAt`, so this is the only refresh of the list and not a duplicate.
- rev-0002 (round 3). Accepted. A patch content save has no `patches:changed` echo: PatchEditor saves `withFrontmatterOf(patch.content, newBody)`, so the frontmatter goes back byte-identical, `PatchService.updateContent` refuses changes to the immutable keys and `applied`, the frontmatter indexer broadcasts only on a changed projection, and the record store writes with `chain: false`. A token on `useUpdatePatchContent` could therefore only absorb another writer's event. `useUpdatePatchContent` no longer registers an own write (no `onMutate`/`onError`/`succeeded()`); its `onSuccess` cache write + list invalidation stay. `useSetPatchApplied` keeps its token (its echo is real). Brief side unchanged. Tests in `useFileWatcher.ownWrites.test.ts`: the "echo absorbed" / "absorbs one echo only" / "failed save hands back" content-save cases are replaced by: body-only autosave → no detail GET (cache keeps PUT hash + last line); `patches:changed` during a content save → detail refetched; same during a failing (409) save → refetched. Comments in `usePatches.ts`, `own-writes.ts` header and the watcher's `patches:changed` branch corrected.

## m10-plan-full-read-and-conflict / p1-l5-l5
- The plan page already read the detail route without `view`/`range`; since m36 that is the whole-file default projection, so the read needed no change. Following the brief unit (performance rule), `useSavePlan` writes the detail cache from the sent content + the PUT's hash/frontmatter instead of refetching the whole plan, and registers an own write (`lateEcho: true`) in `lib/own-writes.ts` (root `plans`): `PlanService.updateContent` always broadcasts `plan:updated` with `threadId: null`, and the plan write goes with `chain: false` / the watcher's suppress token, so there is no `file:changed` and (frontmatter byte-identical via `withFrontmatterOf`) no `plans:changed` echo. The watcher's `plan:updated` branch offers only `threadId === null` events to the ledger; an event naming a thread is an agent's write and always refetches. Versions / list / threads are still queued on the echo; `useSavePlan` keeps invalidating versions, by-thread and the list (the echo may be lost on a reconnect, which does not invalidate).
- `useCreateThreadFromPlan` no longer invalidates the plan detail or the plans list: attaching a thread writes nothing into the plan file (`attachThreadToPlan` only creates and binds a thread), so only the thread listings move.
- 409 banner: shown only for `PLAN_CONFLICT` (other errors keep the generic error strip). "Reload" refetches the detail (one GET, on an explicit click) and then drops the buffer. The 409 body carries `currentContent`, but seeding the cache from it would keep a stale `frontmatter` (title/applied), and the browser has no frontmatter parser (gray-matter is Node-only), so a refetch is the correct reload. A failed refetch keeps the buffer and shows the error.
- `useUpdatePlanTitle` / `useSetPlanApplied` still refetch the detail after a frontmatter write (the PUT/PATCH answer carries no content and the bytes changed). Their echoes are unchanged; not in this unit's reads.
- `src/server/services/plan.ts` was not touched, so the m36 leftover (PlanReadOpts inside the import block, double blank line, `getByThread` opts type) stays for whoever next edits that file.
- Tests: `PlanPage.render.test.ts` now runs the real PlanPage, PlanEditor, usePlan hooks and useArtifactVersions over a faked `fetch` and a faked tiptap binding (the four `[section:0dy3js11]` cases kept). The fake PUT applies the real hash guard. The on-disk side of the 409 path (byte-identical file, no new `file_version` row) and of the long Save is proven on the real route in `src/server/routes/artifacts.test.ts`. Watcher echo cases for plans are in `useFileWatcher.ownWrites.test.ts`.

## m10-plan-full-read-and-conflict / p1-l5-l5 — round 2 (rev-0001..0003)

- rev-0001: `useSavePlan` is the single owner of the keys an own plan Save moves (detail written; versions, `plans-list`, `['plan','by-thread']` invalidated once in `onSuccess`). The watcher's `plan:updated` branch queues nothing (no detail, versions, plans-list or `['threads']`) when the event is absorbed as the own echo. The mutation was chosen as owner rather than the echo, because it runs even if the echo is lost (socket down). A failed Save that had absorbed an event (`failed()` → true) invalidates detail, versions, plans-list and `['threads']`, which is exactly what the watcher skipped. A content save no longer refetches any thread listing.
- rev-0002: the comments in `lib/own-writes.ts`, `useFileWatcher.ts` and the ownWrites test header now say that `threadId: null` is not proof of an own write. Absorbing such an event is safe because of the per-path write lock.
- rev-0003: on `PLAN_CONFLICT` and on a successful Reload, PlanPage clears `error`.
- The m36 leftover in `src/server/services/plan.ts` is now done: `PlanReadOpts` sits below the imports, the double blank line is gone, and `getByThread` takes `PlanReadOpts`.
- orchestrator: m10 p1 round-2 implementer status lacked the required `release` field (otherwise complete, work in the repo); filled with the window's `2.1.48` instead of re-running the portion — the field is a constant of the build.
