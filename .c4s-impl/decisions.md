- 2026-10-27 (setup, decyzja użytkownika): brief 2.1.55→2.1.56 robiony równolegle w `impl/2-1-55-to-2-1-56`; ten branch idzie równolegle z main, konflikty rozwiązuje drugi merge. Brama „next window exists” (2-1-57-to-2-1-58) — wg reguły jeden brief na PR: kończymy ten brief, następny po merge'u.

- 2026-10-27 (u01 implementer): `operation_id` travels by `AsyncLocalStorage` (`src/server/fs/multi-file-operation.ts`), read at the single INSERT site `FileVersionService.recordVersion` — so the `capture` phase and the artifact services that write their own rows (`chain: false`) stamp it alike, without widening `RecordStore.write`, `runChain` or the watcher's event tuple. A nested `runMultiFileOperation` joins the outer id. Rollback restores verbatim bytes through a new primitive call `RecordStore.restore` (the six steps minus serialization), with `expectedHash` = what the operation left, so a file changed meanwhile surfaces its `RecordConflictError` in `MultiFileOperationError.unrestored` and is not overwritten. The handle offers `write` and `move` only (no `remove`: no multi-file caller deletes); callers adopt it in u02. `FileVersionListItem` (REST payload) does not gain `operationId` — no DTO in this window carries it.
- 2026-10-27 (u03 implementer): the patch joins plan and brief with a service-level per-path queue (`PatchService.withLock`, the RecordStore's own path lock cannot hold the read: `records.write` takes it internally). It wraps `updateContent`, `updateFrontmatter` and `markApplied`, so every read-modify-write of one patch file is one critical section; unlike the brief/plan queues it deletes its map entry at the tail. `PlanUpdateContentOpts.changeSummary` removed — no production caller passed it and M10 `bctqi8sw` says the editor's save carries none. Eleven in-scope ACs had no `[ac:]` test; four existing tests were tagged (patch-tools ×3, plans.test ×1), the rest written new. Filed dev-0004 (AC ustawienie-implemented: author `filesystem` / "agent does not read the flag" vs code) and dev-0005 (endpoint says full ArtifactResponse, code answers echo-free since 0.2.86).
- 2026-10-27 (u03 implementer r2, rev-0001): the per-path queue is one helper, `KeyedQueue` (`src/server/fs/keyed-queue.ts`): `then(fn, fn)` so a refused predecessor still releases the key, and only the tail deletes the key's entry once it settles. `PatchService`, `PlanService` and `BriefService` hold a `KeyedQueue` in place of their own `withLock` copies (removed). `RecordStore.withPathLock` was a fourth identical copy and now uses the same helper too (removed). Test: `src/server/fs/keyed-queue.test.ts` (ordering, key independence, release after a throw, map drains to 0, the entry survives while a tail is queued).
- 2026-10-27 (u04 implementer, p1-l2-a): the code already carried the slug-collision policy as `slugConflict: 'reject' | 'suffix'` (default refuse, explicit slug always refuses, five types on `'suffix'`). It is renamed to the spec's `slugCollision: 'error' | 'suffix'` with no alias: the old key is an unknown-key manifest error, a value outside the pair is refused at registration (`manifest-adapter.ts`), and `allocateSlug` suffixes only on `=== 'suffix'`. The MCP/REST `slug` input description no longer claims an unconditional `-2/-3` suffix. dev-0006 (drift). The Host API unversioned-changes entry for 2.1.57 (m33load01, incl. this slot) is p2's — not written here. The `PLUGIN_TOOL_CONFLICT` sentence in z7l89jhf's `mcpServer?` row is likewise p2 (M33 load-time refusal). m13pool0 names `ac` and `diagram` as the direct tier; only `diagram` is (dev-0007), code unchanged. l4crudhl needed no code change (no `createCrudRouter`, the two routers are domain-only); it is pinned by `tests/integration/entities/plugin-registration-contract.test.ts`.
- 2026-10-27 (u04 implementer, p2-l2-l11): `PLUGIN_TOOL_CONFLICT` is enforced at the point a plugin's backend enters the project's pool — `ProjectPluginHostImpl.mountBackend` (ProjectContext build), since a `${type}-tools` server can only be built with the mount context. Server name already registered → `registerMcpServer` throws (no more `Map.set` overwrite; covers host servers too). Duplicate tool name → the facade `createMcpServer` throws `PluginToolConflictError` (code-checked, not `instanceof`, because plugins reach the facade through the bare alias) before the vendor's anonymous "already registered"; `mountBackend` builds each server a plugin registered while mounting ONCE and rethrows only that code, attributed to the registered name; every other factory failure keeps the per-query skip in `buildMcpServers()`. The throw fails the context build (M31), the same posture as the reserved-name refusal; the code is not added to `PluginLoadCode` (no load record carries it). Host servers registered after `mountBackend` are not probed (their factories close over context services built later). Unversioned-changes registry: two 2.1.57 entries (slugCollision slot-added, mentioning the `slugConflict` rename of dev-0006; PLUGIN_TOOL_CONFLICT behaviour-changed); the 2.1.0 minor keeps one item. dev-0008 (endpoint `/restore`), dev-0009 (z7l89jhf "code is behind" sentence now stale).
- 2026-10-27 (u05 implementer, p1-l2-l11): the activation filter lives in the manifest builder only (`buildFrontendManifest(projectId, pool, activation)`), applied AFTER the overlay > npm > envelope precedence: shadowing stays a backend-`loaded` matter (9g96q3pp), activation is a property of the surviving plugin's types (its load record's `contributedTypes`, per tier: base records read per request, overlay records fixed per context). `isTypeActive` = the context's `pluginHost.isActive` — a `config.entities` change already rebuilds the context. The asset routes do not consult activation (the base route is process-global and cannot). The router dep `overlayLoaded: Set` became `overlayRecords` (one source for loaded ids and types). Client: the activation seed moved from `main.tsx` into `boot-plugins.ts` (`seedPluginActivation`); the boot's `mountFrontend` awaits it, closing the race where a manifest answering before `/_meta/entities` mounted every type. `main.tsx`'s pre-paint built-in mount now runs after the seed (a deep link waits on `pluginBootPending`, the existing not-found spinner). No Host API change.
