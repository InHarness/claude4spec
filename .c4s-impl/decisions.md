- 2026-10-27 (u01 implementer): `operation_id` travels by `AsyncLocalStorage` (`src/server/fs/multi-file-operation.ts`), read at the single INSERT site `FileVersionService.recordVersion` — so the `capture` phase and the artifact services that write their own rows (`chain: false`) stamp it alike, without widening `RecordStore.write`, `runChain` or the watcher's event tuple. - 2026-10-27 (u04 implementer, p1-l2-a): the code already carried the slug-collision policy as `slugConflict: 'reject' | 'suffix'` (default refuse, explicit slug always refuses, five types on `'suffix'`). The MCP/REST `slug` input description no longer claims an unconditional `-2/-3` suffix. dev-0006 (drift). The Host API unversioned-changes entry for 2.1.57 (m33load01, incl. this slot) is p2's — not written here. - 2026-10-27 (u04 implementer, p2-l2-l11): `PLUGIN_TOOL_CONFLICT` is enforced at the point a plugin's backend enters the project's pool — `ProjectPluginHostImpl.mountBackend` (ProjectContext build), since a `${type}-tools` server can only be built with the mount context. Server name already registered → `registerMcpServer` throws (no more `Map.set` overwrite; covers host servers too). Duplicate tool name → the facade `createMcpServer` throws `PluginToolConflictError` (code-checked, not `instanceof`, because plugins reach the facade through the bare alias) before the vendor's anonymous "already registered"; `mountBackend` builds each server a plugin registered while mounting ONCE and rethrows only that code, attributed to the registered name; every other factory failure keeps the per-query skip in `buildMcpServers()`. The throw fails the context build (M31), the same posture as the reserved-name refusal; the code is not added to `PluginLoadCode` (no load record carries it). Host servers registered after `mountBackend` are not probed (their factories close over context services built later). Unversioned-changes registry: two 2.1.57 entries (slugCollision slot-added, mentioning the `slugConflict` rename of dev-0006; PLUGIN_TOOL_CONFLICT behaviour-changed); the 2.1.0 minor keeps one item. dev-0008 (endpoint `/restore`), dev-0009 (z7l89jhf "code is behind" sentence now stale).

- 2026-10-27 (u02 implementer, p1-domain): the five consumers run on `runMultiFileOperation`; their own backup/restore loops (`ReferencesService.propagateSlugChange`, `SectionsService.propagateAnchorChange`) are gone. A page write joins an operation through an explicit handle: `MarkdownFileStore.write(relPath, input, op?)` (and the `PagesService` facade) routes through `op.write` when the root has a record store; the hand-rolled rigs without one keep the plain write. `renameSync` writes through `op.write` inside a nested `runMultiFileOperation` (joins `movePage`'s). **M14:** the move and its rewrites are one operation (one `operation_id`), but the `move-page` records say a failed citation sync does not undo the move and the move's refusals keep their codes — so the move is `records.move` (stamped by ALS, not journalled), its refusal is returned out of the operation and mapped (`moveRefusal`), and a failing rewrite calls `op.rollback()` (only the rewrites) before landing in `citationSync.error`. **M18:** `ReferencesService.updateTag(tags, slug, input)` is the one entry (REST route + `update_tag`): refusals are settled first by `TagsService.slugAfterUpdate` (same checks `update` runs), then ONE operation rewrites the pages first and calls `tags.update` last — tags.json and the entity files are file-last copies of index rows (M29), not restorable by bytes without leaving the index behind, so they are written after the last step that could fail. **M19/M29:** the entity-file listeners run inside the same operation after every page write; they write no `file_version` rows (writeSync, no chain) and keep their existing per-listener skip. `walkPages` now hands the visitor the whole page, so a rewrite no longer re-reads the file it just read.
- 2026-10-27 (u02 implementer r2, rev-0001..0003): **rev-0001** — `TagsService.update` runs the UPDATE (and its `entity_tag` FK cascade), `persistTags` and the entity re-persists in one `db.transaction`, so a `tags.json` throw rolls the row back and the index stays on the slug the restored pages carry; the m18acc00 test now fails inside the stub store's `persistTags` and asserts `tag` and `entity_tag` are still on the old slug. **rev-0002** — `refusalBehind(err)` (`src/server/fs/multi-file-operation.ts`), called first by the REST `errorHandler` and the MCP `toolFailure`: a `MultiFileOperationError` whose rollback restored every file and whose cause is a refusal (an `Error` with a string `code`, not a Node I/O error with `errno`) is rendered as that cause — `409 SLUG_CONFLICT`, not `500 INTERNAL`. With any unrestored file the wrapper stays (disk is neither the before nor the after state: a server-side failure). Tested through a real race (a writer takes the slug between `slugAfterUpdate` and `update`) on `PATCH /api/tags/:slug` and on `update_tag`. **rev-0003** — `movePage` reads the rollback's `unrestored`: those pages are still rewritten on disk, so they stay in `citationSync.rewritten` and the error names them; the `CitationSyncResult` doc says what `rewritten` means after a rollback.
