## u3-sidebar-side-menu/p1
- The side menu (`src/client/components/shell/SidebarSideMenu.tsx`) renders its panel through the catalog `Popover` (placement right — anchoring, viewport bounce, click-outside, z-tier), not through `openPopover`. The catalog `Popover` props are pinned to its `ui-kit-component` record, so no `role` prop was added to it: the menu semantics live on an inner `role="menu"` list of `role="menuitem"` links inside the Popover shell.
- "At most one open" is a module-level store (`openMenuId`) shared by every instance; opening one (click or hover) replaces the id, so the previous closes.
- Hover opens, nothing closes on mouse-leave (the spec lists the close paths: item click, Esc, click-outside, Tab/Shift+Tab, opening another). A click on the entry of a hover-opened menu keeps it open; a click on a click-opened one closes it.
- Cmd/Ctrl (any modifier) click on an item is left to the browser (new tab) and does not close the menu in the current tab.
- OTHERS item activity uses the route segment boundary (`/tags` or `/tags/...`), the trigger is highlighted when any item is active. ELEMENTS activity goes through `isElementsEntryActive(pathname, prefixes)`; in this unit each entry still covers one type — multi-type entries (groups) and ELEMENTS entries opening the side menu are u4's.
- The OTHERS fly-out (`OthersTrigger`, `FlyoutLink`) is removed; the e2e `sidebar-others-flyout.test.ts` became `sidebar-others-side-menu.test.ts` (same stacking/viewport/active assertions, now against `role="menu"` / `menuitem`).
- (round 2, rev-0001) The side menu's keydown handler acts only while focus is on its entry or inside its list (`document.activeElement` checked against `triggerRef`/`menuRef`). A hover-opened menu with focus in the editor/an input leaves ↑/↓/Enter/Tab to that field; Esc there closes the menu only through the catalog Popover's own Escape close and focus is not pulled to the entry. The render test opens menus with a focusing click (`openByClick`), as a browser click focuses the button, and a new `[section:l5pkeysm]` test pins the hover-opened/focus-elsewhere case.
- (round 2, rev-0002, non-blocking, fixed alongside since it is the same handler) Tab/Shift+Tab with focus on a menu item first moves focus to the entry, then closes, so the browser's focus move continues from the entry instead of <body>. rev-0003 (unnamed Popover dialog) left open: non-blocking and outside `only`.

## u4-elements-slot/p1
- Composition lives with M13 on the client: `src/client/core/plugin-host/elements-menu.ts` (`composeElementsSlot`, the closed `GROUP_ICONS` list + `groupIcon` with the `folder` fallback). The list is the u5 picker's source. It was not added to the public `ClientPluginHost` interface (that is plugin-facing surface).
- Normalization at render, one rule for every duplicate: the first occurrence in file order wins, whether the later one is a type entry, a hidden entry or a group membership. In a file that obeys rule 5 a type cannot be both hidden and grouped, so "a hidden entry's position does not matter" holds there. A group with a blank label or empty `types` places nothing, so its members fall to the unplaced tail in `sidebarTab.order`. A hidden type is "placed": it is not appended at the end.
- "No entity types configured." still means no active type with a `sidebarTab` (activation). A project whose visible types are all hidden shows an empty section.
- Group counter placeholder: `…` until every VISIBLE member's key is present in the `/entities/counts` answer. The answer carries every active type, so a missing key means not arrived. Type entries keep `?? 0`.
- Layout source (`useElementsMenuLayout`, hooks/useConfig.ts): the `elementsMenu` of the FIRST `['config']` read the page sees, kept in a WeakMap keyed by the QueryClient (one per page load). Later refetches (WS `plugin:reloaded`, an activation change's invalidateAll, another tab's save) do not rearrange the sidebar until reload, which is the activation rule. While the first read is in flight the section renders no entries, so the default order never flashes; an error or project-less `/welcome` falls back to the default order. u5 (own-tab save → sidebar at once) has to update this seed. No setter was added now, because it would have no caller (dead code).
- `isElementsEntryActive` now matches on a segment boundary (`=== prefix` or `prefix + '/'`), like OTHERS' `isOnRoute`. Without that, a hidden type whose prefix merely begins with a visible one's could light the visible entry.
- No `HOST_API_UNVERSIONED_CHANGES` entry was added: that registry mirrors the specification's Host API changelog, and this window's packet carries no changelog entry for `sidebarTab.order` becoming the default order. Only the comments that called it the sole order source were updated.
- u4 r2 (`ac-wpisy-w-sekcji-elements-sidebara-derywow`): the criterion's test moved from `SidebarElementsMenu.render.test.ts` to `Sidebar.elements-derivation.render.test.ts`, which renders the WHOLE `Sidebar` (hooks mocked) so it can show that the Pages tree and the OTHERS menu (with Tags) stay the same whatever the layout and whatever modules are active. "Still active in references" is read as `getEntity`/`isActive`/`listEntities` keeping the tab-less type and `categoriseBrokenChip` returning null for it (chips not broken).
- u4: first review reads the whole unit (baseCommit..HEAD), not only the unit-verifier fix — no review round had run on u4 yet.

## u5-sidebar-menu-editor/p1
- The editor is a `custom` element on `#entities` (id `sidebar-menu`, weight 20, `keys: [['elementsMenu']]`, effect `Applies immediately.`), `src/client/core/plugin-host/SidebarMenuElement.tsx`; its pure list operations live in `sidebar-menu-editor.ts`. Controls are up/down buttons, a "Move … to" select (Top level / each group), Hide/Restore/Remove icon buttons, a label input and an icon select — no drag and drop.
- Every action writes the MATERIALIZED menu into the draft (file entries + every unplaced option as `{ type }`), so a save persists the whole menu. An untouched editor is not dirty and sends nothing.
- Options = types ticked in the Entity types draft (absent ⇒ every registered type) that declare a `sidebarTab`, in `sidebarTab.order`. Label/icon come from `sidebarTab`; an active type unticked in the draft is greyed with its label and stays (not removable); an inactive, unknown or tab-less slug is greyed, shown by slug, kept, and removable (Remove is offered only for those).
- Hide: a top-level type becomes `{ type, hidden: true }` in place; a grouped type leaves its group and is appended as a hidden entry. Restore removes the hidden entry and appends `{ type }` at the end. Delete group splices its types in its place. A moved-out grouped type lands right after its group. New group = `New group` (`New group 2`, … unique case-insensitively) with no types — its rule-4 error holds [Save] until a type is moved in.
- Save rules 2–5 now have ONE implementation, `elementsMenuSaveIssues` in `src/shared/elements-menu.ts` (all issues with entry index and `label`/`types` position); the PATCH rule refuses on the first one (same messages as before), the editor shows each beside the group label / type list and reports the first as the key's live error — only when the key is dirty, so a merge-broken file never blocks an Entity types save. The server's `elementsMenuSaveError` was removed (no callers left). The icon select offers exactly `GROUP_ICONS` plus "Default (folder)" (rule 7, completed from u1).
- Reset to default order drafts `null`; PATCH treats `null` for a field declared `nullRemovesKey` (only `elementsMenu`) as removal: no type check, no rule, `writeConfig(cwd, partial, remove)` deletes the top-level key. Non-blocking deviation dev-0001 (DTO `patch-config-request` has no `null`).
- Own-tab save → sidebar at once: `usePatchConfig.onSuccess` replaces the page's layout seed (u4's per-QueryClient seed) when the body carried `elementsMenu`, and the seed became a tiny external store (`useSyncExternalStore` + listeners per QueryClient), so the sidebar re-renders even when the new config is structurally equal to the cached one. Saves elsewhere still do not move the sidebar until reload.
- u5 review r1: the reviewer marked all 4 findings non-blocking; the orchestrator raised them to blocking — rev-0002 is a performance finding (extra re-render + render-phase store write; project rule: performance findings are always fixed), rev-0001 leaves a merged file unsavable in the editor (user-observable dead end), rev-0003 duplicates the default-order helper (drift risk), rev-0004 breaks repeated keyboard Move. All are small and in the same files.
- u5 r2 (rev-0001): `materializeLayout` applies the slot's rule. A slug occupies one place, and its first occurrence in file order wins: a later type entry, hidden entry or group membership is dropped. So a duplicate left by a merge shows once, as in the sidebar, and the first edit saves the menu without it. A group emptied this way stays, with its rule-4 error, and Delete group clears it. Test: `[section:lbqrd6xh] a type a merge left twice…`.
- u5 r2 (rev-0002): `useElementsMenuLayout` no longer writes the store during render. The seed is derived in render (`stored ?? { layout: data.elementsMenu }`) and persisted in a `useEffect` without notifying listeners. The rendered value is the persisted one, and `getSnapshot` is stable (`useCallback`), so the uSES consistency check sees no change. The app has one consumer (Sidebar); its subscribe check runs before its own persist effect, so there is no extra render.
- u5 r2 (rev-0003): `byDefaultOrder` and `hasSidebarTab` (formerly the private `hasTab`) are exported from `elements-menu.ts`. The editor's options use them, so there is one default-order rule.
- u5 r2 (rev-0004): Type rows are keyed `t:<slug>`; a slug occupies one place after rev-0001. Hidden rows are keyed `h:<slug>`. Groups are keyed `g:<editor id>`. The id is a symbol-keyed property set in `materializeLayout`: object spread carries it, and JSON (dirty check, PATCH body) never sees it. A group read from the file gets its id from a WeakMap keyed by the baseline object, so a move that returns the draft to the baseline keeps it. React can still re-insert a moved node, and a browser drops focus on that, so after a Move the row's same-direction button gets focus back in a layout effect, or the other button once it hits an end.
