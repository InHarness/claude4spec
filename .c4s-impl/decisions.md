## workspace-home-model / p1-l1-l2 (implementer)

- View = `WorkspaceRegistry` read API (`getWorkspace`/`listWorkspaces`/`getProject`/…) composing the stored entry with `workspace.json`; the home file is read once per registry instance and cached (outside change → next start), own writes (`registerProject`, `removeProject`) refresh the cache. `startServer` calls `registry.openView(name)` before listen: `.gitignore` (`local/`) + validation → `WorkspaceFileError` with code refuses the start. Persisted entry type `StoredWorkspaceRecord` (home entries carry `home` + `projectTrust`, no `projects`/`plugins`).
- Trust of a home project: `projectTrust[id] = { path, trustProjectPlugins?, trustSpecSkillHooks? }` in the registry entry; the view folds flags in only while `path` equals the view path, so a moved id reads as undecided (prompt again). Setting a flag under a new path replaces the record (no stale consent survives).
- Slots: M31 owns `slotsDir(ws)` / `slotDir(ws,id)` / `prepareSlot` (continuity + quarantine for home kind); M41 `openDb(slotDir)` / `forgetDbSlot(slotDir)` take the directory from the caller; free `slotDirFor` removed (it ignored the registry home).
- Advisory lock + atomic write extracted to `advisory-lock.ts`, shared by the registry and `workspace.json` (lock in `local/`).
- Out of this unit (left to their units): creating a home entry from `--cwd`, plugin package location (`node_modules` in slots dir), CLI listing of kind/home, activation refusing a dir carrying `workspace.json`. `lastOpenedProject` is written by `touchLastOpened` (both kinds); no reader in this unit.

## lazy-project-activation / p1-l2-l10 (implementer)

- Activation split in `src/server/workspace/bootstrap.ts`: `activateProjectDir` (M01 `dsh8ezbz` steps 1–6: refuse `.claude4spec/workspace.json` with `WorkspaceHomeNotProjectError`, migrations, `loadOrCreateConfig(cwd)` without any flag input, `.gitignore`, root dirs, welcome page), `activateProject` (+ step 7 legacy db move, for a registered project), `activatingBuild` (the cache builder `startServer` uses: activation then `buildProjectContext`), `bootstrapProject` (POST /api/workspace/projects: file steps → registration → db move; shape unchanged). `BootstrapOptions`, `ConfigCliArgs`, `applyPagesDirOverride`, `pagesDirOverride`, `StartOptions.initialProject/pagesDir`, `ServerHandle.writingStyle` and the eager warm are removed.
- Start (`prepareStart`): no project is activated or built before listen. `--create-project` / `--cwd` now only REGISTER the CWD (no mkdir, no config peek/write); the project activates on its first request. `--name` / `--pages` are removed from the parser (their only purpose — project config input — is gone with this unit's goal); the rest of the start-flag rework (`--create-project`, `--cwd` as home) stays with `workspace-selection-at-start`. `--remote-url` no longer implies `--create-project` and is passed raw as `StartOptions.remoteApiUrl` to EVERY project's build (M01 `3ebblo1q`: process-lifetime override, never written); the token/address side stays with `remote-session-issuer`.
- Dropped with the config peek: a pre-v3 `config.json.port` of the CWD no longer selects the workspace at a create-project start (it was a project read+rewrite before listen). The v3 carry (first-wins port/mode into the registry) still happens at the project's activation.
- `$schemaVersion` of a non-number type is refused by both config migrations before any decision (`assertSchemaVersionType`): before, `migrateConfigToV4` stamped `"3"` → `4` silently, against `ac-config-json-type-mismatch-np-schem` ("bez zgadywania konwersji").
- The context build keeps its own `recoverPendingRootRename` + `migrateConfigToV4` pass although the cache's activation ran them just before: `buildProjectContext` is called directly by many tests/helpers on fixture dirs, and the second pass is a read of one small file that writes nothing (no-op). Moving the whole activation into `buildInner` would make every direct build write config/.gitignore/welcome page.
- Activation once per process per (id, dir) — ASSUMPTION:dev-0202: a rebuild after invalidation/eviction is a build, not an activation (no re-created welcome page, no repeated fs steps).
- `effectiveRoots` threading (config route, field registry, plugin MountContext `roots`) kept — it still means "the roots this context was built from"; only its `--pages` rationale in the comments was rewritten.
- Retired criterion `ac-name-my-spec-w-pustym-katalogu-zap`: no test carried its slug; the old `--name` assertion in `[ac:ac-npx-inharness-ai-claude4spec-create]` (launch.test.ts) was removed with the flag.
