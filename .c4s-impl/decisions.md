## u1-release-marker/p1-l2 (implementer)
- "Najpierw historia HEAD, potem wszystkie refy poza cieniami; z trafień wygrywa najstarsze dodanie" built as two sequential searches (HEAD history; then `git log --exclude='refs/runs/*' --all`), the oldest add winning within the search that answered. The release file is immutable, so a marker appears in exactly one commit and the two readings coincide; the sequential form keeps the common case to one git subprocess. The second search never runs when HEAD already answers.
- The unrestricted `--all` search is gone (no flag, no fallback); `findFirstAdd` now takes the ref arguments, and the old `--all` tests were rewritten as `[ac:ac-resolvereleasecommit-uzywa-git-log-all]` (HEAD first, other branch, shadow-only → null) and `[ac:ac-przy-switchafterrelease-off-z-commitem-n]` (named target, switch off).
- M17's consumer (`resolveReignRef`) already falls back to SQLite on a `null` marker, so the M17 changes in this window need only its doc comment; the `isAncestorOfHead` gate and the delta core stay with u2/u3.
- `commitOnRelease` omits `switched` when it did not switch (additive field); the switch-off test reads absence as `false`.

## u2-shadow-git-plumbing/p1-l4-l4 (implementer)
- Shadow filter pathspecs come from the kind declarations, not from new wiring: the effective `pages` roots of the service plus every system root whose kind has the `release` flag (`entities` today), with the `releases` root as a `:(exclude)` pathspec (a page root at `.` would otherwise enclose it).
- "Not an ancestor of HEAD" is decided by `merge-base(HEAD, tip) === tip` — the same subprocess that proves the common ancestor, so each ref costs one `merge-base` plus, when still undecided, one `diff --quiet`; refs are checked in parallel after one `for-each-ref`.
- `diffRefs` now passes its two sides as two arguments (`git diff <a> <b>`) instead of a range — identical for two commits, and it accepts a tree SHA on the right (no extra `cat-file` probe).
- The trial merge (`git merge-tree --write-tree`) is one private helper shared by `sync()` and `mergeTree()`. The git version is read once per process (`git --version`, a failure is not cached); `supportsTrialMerge(version)` is pure, so the old-git path is tested by injecting the version. `sync()` itself gets no version gate in this unit (the tech-stack part names `mergeTree`'s 'unsupported').
- `resolveShadow` and `mergeBase` have no production caller yet — they are the contract the M17 shadow diff (later unit) consumes; they are tested against a real repo here.
- Fetch and sync run the shadow fetch (`git fetch --prune <remote> +refs/runs/*:refs/runs/*`) after the upstream fetch, under the same lock; a failure of either is `error`.
- u2 review round 1: rev-0001 (unbounded per-shadow git fan-out, errors swallowed as 'no merge base') promoted to blocking per the performance rule; rev-0002 (resolveShadow accepts revision suffixes like `~1`/`@{1}`) promoted to blocking — it feeds u4's unknown-shadow refusal. The reviewer omitted `portion`; the unit has one portion, filled in by the orchestrator.
- u2 round 2 (implementer, rev-0001): `listShadows` drops the ancestors of HEAD inside the one `for-each-ref --no-merged=<HEAD>` (no per-ref subprocess for them; the `base === tip` check is gone with it), then checks the remaining refs through `mapBounded` at most `SHADOW_SCAN_CONCURRENCY` (4) at a time. `mergeBaseAt` returns `null` only for git's exit 1 (no common ancestor) and rejects otherwise; `listShadows` logs a failed merge-base / diff as a failure naming the shadow, `mergeBase`/`resolveShadow` map it to `null` with a warning — the shadow layer still never throws (contract eu1rffp6), so a failed ref is left out of the list rather than failing the GET.
- u2 round 2 (implementer, rev-0002): `resolveShadow` no longer builds a revision expression from the id. It lists `refs/runs/<id>` with `for-each-ref` (same reader as the listing) and takes the tip only of the ref whose name equals the id exactly; `~1`, `^`, `@{n}`, globs, a prefix or an empty id match no ref name → `null`. One subprocess, no extra `show-ref`/`check-ref-format` spawn.

## u3-two-state-delta-core/p1-l2 (implementer)
- The core is a module of plain functions, `src/server/services/git-two-state-delta.ts` (`computeTwoStateDelta(deps, stateA, stateB, roots)`), not a `ReleaseService` method: its inputs are two states (commit-ish or tree SHA) and `DeltaRoots` (pathspecs, page roots, entities root + parser, excluded dirs, optional exact-page filter); it takes no release row and no database, and returns only `{ entities, pages }`. `null` = no M28 file list (git off / no repo / failed diff); the caller decides.
- `tryGitAnchoredDiff` keeps only the caller's part (reign states via `resolveReignRef`, the same-state decline, the `from`/`to` meta) and no longer calls `diffRefs` itself; the one `diffRefs` call is inside the core. `resolveGitDiffScope` now builds `DeltaRoots` (its unused `config` parameter is gone).
- "korzeń entities → diff encji hosta na payloadach obu stron": the git track's entity rows were status-only (`changes: []`) plus a stamp-only filter. They are now the host diff of both sides' payloads (envelope stripped with `stripFileEnvelope`, brought to the current shape with `upgradeCapture`), as the SQLite track does with captures; a system-fields-only change is the host's `noop`. Unreadable/unparseable side → the status-based row, `changes: []` (report, never hide). `_serializerVersionMismatch` is set when the two files' `payloadVersion` differ.
- The unreleased track (`:to = current`) compares a state with the working tree — not a state, so not the core — but reuses the core's `classifyChangedFiles` / `diffChangedPages` / `diffChangedEntities` with a working-tree reader. So `ReleaseService.classifyGitDiffFiles`, `diffPageCandidates`, `dropStampOnlyEntityChanges`, the two status maps and `PageCandidate` are removed (no second implementation left). Side effect: `GET /diff/current` with git on now carries per-field entity `changes` too.
- Performance: page and entity reads are both bounded (`DELTA_READ_CONCURRENCY` = 8; pages were an unbounded `Promise.all` before) and run one after the other so the bounds don't add up; the repository probe (`detect()`) runs once, in parallel with the file list. `mapBounded` is exported from `git.ts` and reused rather than duplicated.
- rev-0001 (round 2): the doubled probe is gone. New `GitService.probeRepo()` — gated on `config.git.enabled` (git off spawns nothing), ONE `rev-parse --show-toplevel`, returns `GitRepoRoot` (`{detected, rootPath}`), not the full `detect()` (remote, branch, whole-tree `status`) which none of these reads need. `diffRefs` and `diffRefToWorkingTree` gained an optional `precomputedStatus?: GitRepoRoot` (like `showFile`, whose param is widened to the same type). `computeTwoStateDelta` and `tryGitAnchoredUnreleasedDiff` take one `probeRepo()` and hand it to the file list and every `showFile`; `DeltaDeps.git` no longer picks `detect`. Tests: `[review:rev-0001][section:0jsqpl74]` in `git-two-state-delta.test.ts` (one probe, no `detect`, one `rev-parse` subprocess, same probe object everywhere, zero spawns with git off) and in `release-diff-git.test.ts` (unreleased path).
- u3 review round 2: rev-0002 (non-blocking, duplicate git.enabled gate) applied by the orchestrator — `shadowLayerRoot()` = `(await this.probeRepo())?.rootPath ?? null`; behaviour identical, typecheck green.

## u4-shadow-diff/p1-l2-l4 (implementer)
- The M17 owning core is `computeShadowDiff` in its own module `src/server/services/release-shadow-diff.ts`; `ReleaseService.shadowDiff(ref)` (the L2 API method) only hands it the git primitives, the page serializer, the host and the scope (the release diff's `DeltaRoots`, every registry root dir — the page roots plus `SYSTEM_ROOTS` — and the `releases` dir). No release row, no SQLite read: no git service / git off / no repository → `GIT_UNAVAILABLE`.
- One repository probe per request: `probeRepo()` once, handed to `resolveShadow`, `mergeTree`, `listCommits`, `diffRefs` and the core. `resolveShadow` and `mergeTree` gained an optional `precomputedStatus` (like `diffRefs`/`showFile`); `computeTwoStateDelta` gained `opts: { repo?, deletedBefore? }` — the defaults keep u3's single-probe behaviour.
- `resolveShadow` now also returns `headSha` (additive field): HEAD is read once (`rev-parse HEAD^{commit}`, in parallel with the ref lookup) and `merge-base`/`rev-list` run on that SHA, so `head.sha`, `base.sha` and `masterAhead` belong to the same HEAD and the trial merge is run on it (`mergeTree(headSha, tipSha)`) — no `HEAD` symbol resolved twice. The two u2 tests that compared the whole object now expect `headSha`.
- "before" (0xvhubti) is collected by the core while the entity diff reads the left side (`deletedBefore` map in `diffChangedEntities`) — no second `git show`. The value is the entity file's payload as the diff compared it (envelope stripped, upgraded to the current shape), not the raw file text. A deleted entity whose left file is unreadable/unparseable gets no `before` entry (its delta row stays file-level).
- Flags (nemiv2qh) read the shadow's own change `merge-base..tip` over the whole repository with ONE `diffRefs(base, tip, [repoRoot])`; paths outside every registry root → `outsideSpecFiles` (repo-relative, sorted, deduped), any path in the `releases` root → `touchesReleases`. Commits come from the new read-only primitive `GitService.listCommits(from, to)` (`git log --format=%H%x00%s%x00%b%x1e`, newest first, body trimmed). The core delta, the flags' file list and the commit list run in parallel.
- `conflicts` and `outsideSpecFiles` are repository-relative paths (what `git merge-tree --name-only` answers).
- The route is a thin adapter (`src/server/routes/shadow-diff.ts`, `GET /?ref=`), mounted at `/api/shadow-diff` beside `/api/releases`; a non-string/empty/repeated `ref` → `400 VALIDATION`. `SHADOW_NOT_FOUND: 404` and `GIT_UNAVAILABLE: 400` were added to `STATUS_FOR_CODE`.
- Catalog: row `shadow_diff` (rest direct, the other three `n/a` with the record's reason), its rules in `OPERATION_RULES`, and the record added to `tests/helpers/spec-operation-records.ts` (78 → 79 in the whole-catalogue test).
- `module-dependency m17-requires-m28` is context (no counterpart): the dependency is realised by M17 consuming the M28 primitives.
- dev-4601 (non-blocking): a `mergeTree` `error` on a supported git is a 500, not a fall to `shadow-only`.
- u4 review round 1: reviewer's rev-0001 (missing releaseStore reported as GIT_UNAVAILABLE) promoted to blocking (cheap); orchestrator added rev-0002 — public `GitService.mergeBase` from u2 has no production caller once u4 reads `baseSha` from `resolveShadow` (user rule: unused code is always removed); the merge-base capability of the eu1rffp6 contract stays, exposed through `resolveShadow`.
- u4 round 2 (implementer, rev-0001): `ReleaseService.shadowDiff` answers `GIT_UNAVAILABLE` only when no git service is wired (git off / no repository come from `computeShadowDiff`'s probe); a missing release store throws a plain `Error` (500, "release store is not wired") from `resolveShadowDiffScope`, i.e. only once the comparison actually needs the `releases` root — git off still refuses with `GIT_UNAVAILABLE` even when the store is missing. Test `[review:rev-0001]` in `src/server/routes/shadow-diff.test.ts`.
- u4 round 2 (implementer, rev-0002): public `GitService.mergeBase` removed (no caller). Its tests now prove the merge-base answer through `resolveShadow(...).baseSha` (incl. a shadow grown on HEAD → `baseSha = HEAD`, `masterAhead 0`), no common ancestor → `null`, a failed merge-base → `null` + warning (never throws), git off / no repo → `null`; private `mergeBaseAt` stays (used by `listShadows` and `resolveShadow`).
