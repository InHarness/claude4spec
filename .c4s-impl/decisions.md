- 2026-10-27 (u01 implementer): `operation_id` travels by `AsyncLocalStorage` (`src/server/fs/multi-file-operation.ts`), read at the single INSERT site `FileVersionService.recordVersion` — so the `capture` phase and the artifact services that write their own rows (`chain: false`) stamp it alike, without widening `RecordStore.write`, `runChain` or the watcher's event tuple. A nested `runMultiFileOperation` joins the outer id. Rollback restores verbatim bytes through a new primitive call `RecordStore.restore` (the six steps minus serialization), with `expectedHash` = what the operation left, so a file changed meanwhile surfaces its `RecordConflictError` in `MultiFileOperationError.unrestored` and is not overwritten. The handle offers `write` and `move` only (no `remove`: no multi-file caller deletes); callers adopt it in u02. `FileVersionListItem` (REST payload) does not gain `operationId` — no DTO in this window carries it.
