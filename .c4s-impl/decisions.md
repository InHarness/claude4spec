- implementer contribution-scope/p1-m13-m33 (2026-11-14): the "declared Host API version" of a plugin is `semver.minVersion(manifest.hostApiVersion)` — the lowest version its range admits, the one its author wrote against; its set is that of the latest release at or below it (`HOST_API_RELEASES[].contextTypes`, a minor inheriting the previous set unless it announces one). A range below the oldest release, or unreadable, gets the oldest (narrowest) set. ASSUMPTION:contribution-scope-declared-version.
- implementer contribution-scope/p1-m13-m33: the loader leaves an omitted skill `contextTypes` unchanged (M33 `emco4ju2`) and records the declared set beside the entry (`contribution-scope.ts`, a WeakMap keyed by the admitted contribution); `fanPluginSkills` hands it to `SkillRegistry.addPluginSkill`, whose plugin source stores it as the entry's scope. The loader carries it explicitly as `ScopedPluginSkill` (`PluginRegistry.listScopedSkills()`, `ProjectOverlayResult.scopedSkills`), and `fanPluginSkills` reads it from there. `SkillRegistry.addPluginSkill` falls back to the running set only for pushes with no package behind them, such as direct test pushes and `addPluginStyle`.
- contribution-scope rev-0002 (fixed): a subagent whose explicit `contextTypes` names a value outside its declared Host API version's set loses the WHOLE entry, with a warning, at loader admission (`admitSubagentContextTypes`, both base and overlay layers). An omitted value (`['chat']`) and a non-array value stay with the per-turn resolver.
- implementer consultation-entry/p1-l1-l19 (2026-11-15): stub `context-registry → consultation-entry` closed. `chat_thread.consultation` is written only by `ChatService.createThread({ consultation: true })`, which only `POST /api/threads` with `entry: "consultation"` reaches. Its turn effects key on `ChatService.isConsultationThread(thread.id)`, not on `context_type === 'ask'`: the peer-turn background-task switch (`agent-turn.ts`, next to the row's `Zadania w tle` and the child-thread switch) and the consultation answer processing (`threads.ts` POST /:id/ask).
- implementer consultation-entry/p1-l1-l19: the generic create-thread route reads the project registry from `AgentTurnDeps.contextTypes`; when absent (rigs), it uses every row (`rowsOfRegistry`). A value outside the registry and a value without `nowy wątek` are both `400 VALIDATION`, with different messages.
- implementer consultation-entry/p1-l1-l19: `runAgent` has no closed list of `contextType` (now `string`). The project registry lives on the server, so `--ct` outside it is refused by `POST /api/threads` (`VALIDATION`), and `runAgent` maps that to `INVALID_ARGS`, the code the `agent` record names. With `--ct` omitted, the engine sends `{}`, so the server picks `Wejście: domyślny`. It no longer sends a client-side `'chat'`. The consultation is `runAgent({ consultation: true })`, used by `c4s ask` and `c4s-tools.ask`. It sends `{ entry: "consultation" }` and refuses any context argument next to it with `INVALID_ARGS`.
- implementer consultation-entry/p1-l1-l19: the `create_thread` operation record (`core-operations.ts`) is unchanged: its spec-operation did not change in the window, and it is outside this unit. Its summary and its `context_type` description still say "chat or ask", and its codes stay `['VALIDATION']`, although the route now also answers `PROJECT_WITHOUT_CONSULTATION`.
- implementer consultation-entry/p1-l1-l19: `ac-mcp-tool-ask-propaguje-wszystkie-strin` reads `tool_result.error.{code,message,hint?}` as the tool's existing error result: `isError` with the flat envelope `{ error: <message>, code, hint? }` (item 3, unchanged here).
